# Aetheria: research and architectural tradeoffs

Research checked against the current `shared/`, `client/` and `server/` code on 2026-09-17. The references below were successfully fetched during this documentation pass. They explain platform/library contracts; they do not validate Aetheria's correctness or performance. This is an original implementation using general programming documentation, not Minecraft sources, decompiled code or extracted assets.

## Sources

1. **Three.js — BufferGeometry**: https://threejs.org/docs/pages/BufferGeometry.html. Documents vertex/index/normal/color/UV buffers, bounds and explicit GPU-resource disposal.
2. **MDN — Using Web Workers**: https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers. Documents background computation, message passing, module-relative worker URLs and transferable buffers. This is a browser-platform guide, not a game-engine tutorial.
3. **ws maintainers — README**: https://github.com/websockets/ws/blob/master/README.md. Documents native browser WebSockets versus Node `ws`, HTTP upgrade handling, application-owned authentication and the CPU/memory tradeoff of per-message compression.
4. **Node.js — File system**: https://nodejs.org/api/fs.html. The fetched current page identified itself as Node v26.9.0; Aetheria targets Node 24 and uses long-established `fs/promises` APIs, not new v26-only APIs. Relevant sections are `fsPromises.rename(oldPath, newPath)`, `filehandle.sync()`, `fsPromises.copyFile()` and ordering of promise-based operations. The rename API has existed since v10.0.0; the docs explicitly do not guarantee copy atomicity.

These are live documentation URLs, not pinned dependency specifications. Use `package-lock.json` for the installed dependency resolution.

## Decisions grounded in current code

| Area | Current choice and reason | Cost / alternative |
| --- | --- | --- |
| Chunk rendering | Indexed `BufferGeometry` collects exposed faces into solid and liquid meshes per chunk; one generated atlas supplies face UVs. This avoids a separate mesh/material per voxel and matches the buffer API [1]. See `client/rendering/mesher.ts:14`, `client/rendering/world.ts:182`, `client/rendering/atlas.ts:6`. | This is exposed-face meshing, **not greedy meshing**. Adjacent coplanar faces are not merged; a more compact mesh requires additional logic and texture/shading constraints. Transparency and partial-block boundaries remain QA concerns. |
| Worker ownership | A small worker pool meshes copied, padded chunk snapshots; job inputs and result attribute buffers are transferred. Revisions reject obsolete results, and evicted meshes dispose geometry [1][2]. See `client/rendering/world.ts:118`, `client/mesh.worker.ts:8`. | Buffer transfer relinquishes ownership; the code therefore transfers a job snapshot, not the live chunk cache. Padding, queues and GPU upload still cost time/memory. Workers move meshing off the UI thread, not all game work; there is no benchmark proving a particular frame rate. |
| Procedural world | Seeded noise and world-coordinate queries generate Verdant, Cinder and Aether in `shared/worldgen.ts:11`; fixed chunks are 16×80×16 (`shared/constants.ts:1`). Trees/structures are generated with neighboring spatial context. | Seed-plus-edits is compact, but changing the generator can change untouched terrain in old saves. There is no general generator-migration system. This is bounded vertical terrain, not arbitrary-height streaming. |
| Cache and replication | The server keeps an LRU-style generated-chunk cache, capped by `min(384, BALANCE.maxChunks)` per world; edited block overlays remain separate (`server/world.ts:16`). Initial chunks use RLE number arrays; subsequent edits are block messages to subscribers (`server/main.ts:86`, `server/actions.ts:14`). | The cap does **not** bound total process memory: edits, profiles, worlds and entities are separate. RLE favors repeated runs but alternating data and JSON encoding may be larger; a binary codec is a future profiling-driven alternative. Saves store sparse edits, not RLE full chunks. |
| Networking and authority | Native browser WebSocket connects to Node `ws` over the same HTTP server [3]. Clients send input intent; the server runs shared physics at the configured tick and owns collision, health, inventory and world mutations (`server/main.ts:85`, `server/main.ts:110`). The client predicts movement and corrects from server state. | Client prediction improves responsiveness but can visibly correct under delay; this is not deterministic lockstep. Client-provided positions are not the normal movement authority. Server authority and validation are safeguards, **not a claim of cheat-proofness or a completed security audit**. |
| Compression and limits | `perMessageDeflate` is disabled; incoming messages have a payload cap, parsing checks, session budgets and chunk-range restrictions (`server/main.ts:38`, `server/protocol.ts:30`). The `ws` README warns about compression CPU/memory overhead [3]. | JSON is easy to inspect but verbose. Rate budgets are per connection, not a complete abuse-prevention layer. Upgrade origin/host checks are not authentication. Public hosting needs a separate security design. |
| Local identity | The browser creates a random bearer token; persistence indexes SHA-256 hashes and compares the creator hash for admin commands (`client/ui.ts:58`, `server/storage.ts:17`, `server/actions.ts:197`). `ws` deliberately leaves authentication to the application [3]. | Hashing avoids saving the raw token, but does not provide TLS, accounts, access-controlled worlds, recovery, rotation or revocation. Any holder of the token can act as that profile. It is appropriate only as a prototype identity mechanism on a trusted host/network. |
| Persistence | A queued save serializes each world, writes/syncs/closes a same-directory temporary file, copies the old primary to a rolling backup, and renames the temporary over the primary (`server/storage.ts:56`). Loading falls back to the backup (`server/storage.ts:25`). Node documents these operations individually [4]. | Avoiding in-place overwrite reduces torn-primary risk, but this is not a multi-file transaction. Backup copying is not atomic, directories are not explicitly synced, schema checks are limited, and multiple server processes are not coordinated. A database/journal and independent backup policy would be needed for stronger durability guarantees. |

## Visual and simulation boundaries

The atlas is produced locally with canvas and seeded texture detail (`client/rendering/atlas.ts:6`). Meshing computes directional/column shading and local ambient occlusion (`client/rendering/mesher.ts:18`), not a propagated voxel-light field. Liquid geometry is a rendering representation, not fluid simulation. Runtime mobs and visual effects also use randomness; “seeded realms” does not mean the entire simulation is replay-deterministic.

Aetheria currently favors a small, inspectable implementation over the full requested game scope. Functional beds/doors, crop stages, hoppers, circuits and bosses are parallel work pending integration/QA; vehicles, rails, villager professions, raids, alchemy, true voxel lighting, dynamic fluids and shaped crafting are not complete systems. The [README](../README.md) and [worklog](worklog.md) distinguish source observations from executed checks.

## Measurement policy

Configured player/cache limits and HUD statistics are not benchmark results. Before increasing scope or declaring readiness, measure representative chunk generation/meshing, frame times, network traffic, cache eviction, save latency and multi-client behavior on named hardware. Record the seed, settings, browser, Node version and commands alongside results. No manual QA, capacity, FPS or save-durability measurements are asserted by this research pass.
